Watch-outs for either choice

Supabase's free tier pauses a project after about a week with no activity, which would make the app fail until you un-pause it. Use the paid tier, or a small scheduled ping. Also choose regions near you (for example Supabase Canada Central, or Cloud Run Montréal/Toronto) and make sure the database enforces SSL.

The architecture change

From a file on one machine to a database any number of copies can share

Now

Browser / phone→Next.js (one copy)→JSON file + memory

Breaks as soon as the host restarts or runs a second copy. Postgres only receives part of the data.

Target

Browser / phone→Next.js (any number of copies)→Postgres (pooled)

Every read and write goes to Postgres. No state is kept in memory or on disk. Backups come from the database.

The plan, in order

Seven phases

Phases 0 to 4 are the web launch. IDs in brackets (S1, D1…) refer to the anomaly register in production-plan.html. The prompts for each phase are in AI_PROMPTS.md.

P0Close the security holes blocks launch

1 day
  • Upgrade Next.js to the latest 15.5.x (15.5.16 or newer) to fix the login bypass and the critical advisories (S1, S2)
  • Check the login inside every API route, not just in the middleware, and add a test that fails if a new route forgets to (S4)
  • Remove the unused ai and @google/genai packages (S3)
  • Require a 12+ character passcode in production; you choose a new one and store it in the host's secret settings (S5)
Done when: the bypass header returns 401 for API and pages, every route is covered by the login test, and the audit shows no critical or high issues in the web app.

P1Move everything to Postgres blocks launch

4–6 days
  • Extend the schema with what the app already uses but the database lacks: opening balance, APR, due date, minimum payment, notes, reviewed flag, exclude-from-reports flag, soft delete (the trash), pay/income settings, login-attempt records, and owner_id everywhere (B6)
  • Real migrations (prisma migrate), not db push
  • Rewrite the data layer on Prisma with the same method names and results, so the web and mobile code keep working; keep the 29 existing data tests as the specification
  • One-time import of your current ledger with a report proving 4,159 rows and all 13 balances match
  • Remove the JSON store, in-memory trash and in-memory login limiter (B7, S7)
  • Serverless settings: pooled connection for the app, direct connection for migrations, one Prisma client per instance, correct binary targets
  • Test database in Docker for local runs and CI
Done when: all tests pass against Postgres, the import reproduces today's numbers exactly, and two copies of the app running at once see each other's changes.

P2Make the numbers trustworthy blocks launch

3–4 days
  • Transfers: pair internal transfers and leave them out of totals; treat e-transfers in or out as income or spending (D1)
  • Data-health screen with one-click fixes: type vs sign, duplicates, zero amounts, unpaired transfers, stale accounts, opening-balance gaps (D2, D3, D6, D8)
  • Exclude-from-reports flag replaces the "Adjustments not to consider" category and is honoured everywhere (D4)
  • Reviewed flag and bulk "Mark reviewed" so the queue can reach zero (D5)
  • Sorting by amount uses size, not sign (B3)
  • You enter each card's APR and due date; resolve the $116.40 CIBC gap (D6, D7)
Done when: the transfer net is near zero, the review queue is under 50 and clearable, and one full month's totals match your statements.

P3Manual-first product

3 days
  • Delete the Plaid simulation, its store entries and both "Connect Bank" buttons (B2)
  • Income settings: sources with amount, frequency (weekly, every two weeks, twice a month, monthly), next pay date and deposit account; one-off expected income and bills; the forecast uses these plus your real average spending, and your own date and timezone (B1)
  • Better CSV import: presets for CIBC, TD, RBC, Amex and Rogers files, column mapping with a preview, skip duplicates, undo a whole import
  • Remove hard-coded claims: transaction counts, "Active" reminders, the Supabase guide; keep redirects' query strings; self-host fonts (B4, B5, S8)
  • Make the seed script opt-in and free of personal sample data (B8)
Done when: searching the source for "simulate", "Plaid", "4,159" and "751.30" finds nothing that reaches users, and changing your pay in Settings changes the forecast.

P4Deploy, protect and watch web launch

3 days
  • Two environments (staging and production), each with its own database and secrets; never share data
  • Deploy to Vercel (or Cloud Run) with your domain and HTTPS; secure cookies on
  • CI on every push: install, type-check, tests against Postgres, build, dependency audit
  • Browser smoke tests (Playwright): login, date filter, export, report, bulk type change, delete and undo
  • Backups: daily database backups with a tested restore, kept 30 days (O2)
  • Monitoring: error tracking, an uptime check on /api/health, alerts for repeated login failures
  • Runbook (docs/RUNBOOK.md): deploy, roll back, restore, rotate secrets
  • Optional: bill reminders by email from a scheduled job
Done when: a push to main deploys to staging automatically, production is promoted by hand, a restored backup opens correctly, and a deliberate error appears in monitoring.

P5Mobile app after web

5–7 days
  • Build setup: icons, splash, eas.json with development, preview and production profiles, bundle IDs, versions, API address per profile (M1)
  • Run on a real phone against staging and fix what breaks (M2)
  • Face ID / fingerprint lock when the app opens or returns from the background (M3)
  • Catch up with web: date range, filters, search across everything, add transaction, mark bill paid (M4)
  • Tests for the sign-in, cache fallback and 401 handling; distribute through TestFlight and the Play internal track
Done when: a preview build on your phone shows live data, locks with biometrics, and shows the offline banner when the network is off.

P6Ready for more users later

5–8 days
  • Real accounts (Supabase Auth or Auth.js) replace the shared passcode; invite-only sign-up
  • Every query scoped by owner in code, with database row-level security as a second lock
  • Sessions you can revoke, "sign out everywhere", passkeys or one-time codes (S5, S6)
  • Per-user limits, an audit log, "export my data" and "delete my account"
  • Load test and add the database indexes the results call for
Done when: a second test user can't see or change the first user's data by any route, including by guessing ids.

What changed from the first plan
  • The database move went from an optional last phase to P1, before launch.
  • The "run exactly one instance" rule and the persistent-volume advice are gone; Postgres removes the need.
  • "Detect my pay from the ledger" became a Settings screen you fill in.
  • Plaid or real bank links are out; manual import and entry get the effort instead.
  • owner_id on every table is new, so multi-user later is cheap.
  • The Docker image matters only if you choose Cloud Run.
